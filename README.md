# Go 设计模式实战 🎯

> 写给每一位「想写出更干净代码」的 Go 后端工程师。

你好呀 👋 欢迎点进来。

如果你现在写代码时，经常有这种感觉：

- 「这段 if/switch 越写越长了，我是不是该重构一下？」
- 「加个新功能，怎么要改这么多地方？」
- 「别人说的『工厂』『策略』到底是个啥，看了定义还是不会写？」

那这个仓库就是为你准备的。

这里不讲晦涩的理论，**每一个设计模式都用一个你能在真实后端项目里遇到的场景**来讲清楚：配一个能直接 `go run` 跑起来的例子，再加一份中文文档。学完一个，你就知道它「为什么存在、什么时候用、能带来什么好处、什么时候千万别用」。

---

## 一、先想清楚一个问题：我为什么要学设计模式？

设计模式不是「背答案」，而是前人踩过无数坑之后，总结出来的一套**解决特定问题的套路**。

它解决的不是「怎么写代码」，而是「代码怎么**改**起来不痛苦」：

- 需求天天变，怎么让改动集中在一个小角落，而不是到处爆炸 💥
- 团队协作时，怎么让别人一眼看懂你的结构
- 怎么把「会变的东西」和「不变的东西」分开

所以学设计模式，请始终带着一个念头：

> **这个模式，是在帮我应对「哪一种变化」？**

搞懂这一点，比记住类图和定义重要一百倍。

## 二、这个仓库怎么用？

每个设计模式一个文件夹，结构都一样：

```
singleton/                  ← 模式名
├── README.md               ← 讲人话的文档（场景、优势、何时用/不用）
├── main.go                 ← 可运行的示例代码（带中文注释）
└── singleton_test.go       ← 单元测试（顺便学 Go 测试怎么写）
```

**运行某个例子**（在项目根目录执行）：

```bash
go run ./singleton      # 换成对应文件夹名即可
```

**运行所有测试**：

```bash
go test ./...
```

**建议的学习姿势**：

1. 先看文件夹里的 `README.md`，搞懂「它解决什么问题」
2. 再打开 `main.go`，从上往下读一遍，配合注释理解
3. 自己动手 `go run` 跑一下，改改参数看输出变化
4. 最后合上代码，问自己一句：**我最近写的哪个功能，其实可以套这个模式？**

## 三、目录导航 🗺️

设计模式通常分成三大类，我也按这个来排。**建议从上往下学**，创建型最简单也最常用，行为型里的「策略 / 责任链 / 观察者」是后端最高频的三个。

### 🏗️ 创建型 —— 解决「对象怎么创建」的问题

| 模式 | 一句话理解 | 后端典型场景 |
| --- | --- | --- |
| [单例模式 singleton](./singleton/) | 全局只有一个实例 | 配置、日志器、数据库连接池 |
| [工厂模式 factory](./factory/) | 把「创建谁」的决定交给工厂 | 多种支付方式、多种消息通知 |
| [建造者模式 builder](./builder/) | 一步步把复杂对象搭起来 | 构造参数超多的配置/请求对象 |
| [函数选项模式 functional-options](./functional-options/) | Go 专属：可选参数的神器 | 几乎每个 Go 库的构造函数 |

### 🧩 结构型 —— 解决「对象怎么组合」的问题

| 模式 | 一句话理解 | 后端典型场景 |
| --- | --- | --- |
| [装饰器模式 decorator](./decorator/) | 不改原代码，一层层加功能 | HTTP 中间件、加日志/缓存 |
| [适配器模式 adapter](./adapter/) | 把不兼容的接口「翻译」过来 | 对接不同第三方 SDK、多数据源 |

### 🤝 行为型 —— 解决「对象怎么协作」的问题

| 模式 | 一句话理解 | 后端典型场景 |
| --- | --- | --- |
| [策略模式 strategy](./strategy/) | 算法可随时替换 | 折扣/计价、灰度路由 |
| [观察者模式 observer](./observer/) | 一件事发生，通知一群人 | 订单成功后发短信/邮件/扣库存 |
| [责任链模式 chain-of-responsibility](./chain-of-responsibility/) | 请求沿链条一个个试 | 中间件、审批流、参数校验 |
| [模板方法模式 template-method](./template-method/) | 固定骨架，细节可替换 | 数据导入导出、支付流程 |

## 四、几句掏心窝的建议 💡

1. **别为了用而用。** 设计模式是工具，不是目标。一个简单的 if 能搞定的，硬套模式反而是负担。判断标准永远是：这样写，以后改起来会不会更轻松？

2. **Go 和 Java 不一样。** 很多设计模式是「经典四人帮」用 Java 讲的，但 Go 没有继承，只有组合和接口。你会发现同样的模式在 Go 里写法更简洁——比如单例用 `sync.Once`，模板方法用函数而不是抽象类。别生搬硬套。

3. **记「场景」比记「名字」有用。** 面试也好、写代码也好，真正救你的是「这个场景我见过，该用 X 模式」，而不是背出 23 种模式的定义。

4. **先跑起来，再想原理。** 代码就在那里，改一行、跑一次，比看十遍文档都管用。
