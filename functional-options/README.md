# 函数选项模式（Functional Options）

> **一句话**：Go 的「官方宠儿」——用**可变参数 + 函数**，给构造函数提供优雅的可选配置。

## 它为什么是「Go 专属」？

很多设计模式是通用语言都能用的，但**函数选项模式几乎是 Go 社区独有的惯用法**（俗称「Rob Pike 的 self-referential functions」，由 Go 语言之父 Rob Pike 推广）。

原因很简单：Go **没有函数重载，也没有默认参数**。Java 里可以写好几个重载构造函数，Go 里不行；Python 里能写 `def f(a, b=10)`，Go 里也不行。

于是 Go 社区发明了这个模式，来解决同一个问题：**怎么让一个构造函数，既能接受「不传任何可选参数」，又能接受「传任意组合的可选参数」？**

## 它解决什么问题？

还是同一个「参数多」的老问题（和建造者模式的场景重叠），但用更简洁的方式：

```go
// 想要：调用方想传几个可选参数就传几个，其余用默认值
server := NewServer()                                  // 全默认
server := NewServer(WithPort(9090))                    // 只改端口
server := NewServer(WithHost("0.0.0.0"), WithTimeout(60)) // 组合改几个
```

对比一下没有这个模式时，你可能被迫写的「丑陋方案」：

```go
// 方案A：传一个巨大的 config 结构体，但很多字段其实是可选的
// 方案B：构造函数签名有 10 个参数，调用方传一堆零值占位
// 方案C：构造函数返回后，再手动改字段（容易漏、不优雅）
```

函数选项模式把这一切变得干净又灵活。

## 应用场景（Go 后端）

**几乎无处不在**。你日常用到的绝大多数 Go 库，构造函数都是这种写法：

- 数据库连接：`sql.Open` 之后的各种驱动配置（其实 `gorm`、`ent` 等 ORM 的配置也常这样）
- HTTP 客户端：`net/http` 的 `http.Client{...}` 结合各种 option
- gRPC：`grpc.NewServer(grpc.Creds(...), grpc.MaxRecvMsgSize(...))`
- 各种 SDK、日志库（`zap`、`zerolog`）、配置库

**一句话：学会它，你就能看懂 Go 生态里 80% 的构造函数。**

## 优势 ✅

1. **零侵入**：不传任何 option 时，调用就是 `NewServer()`，和普通构造函数一模一样
2. **极度灵活**：可选参数想传几个传几个、顺序随意、未来加新 option 不影响老代码
3. **可读性好**：`WithTimeout(60)` 自带语义，比裸的 `60` 清楚太多
4. **向后兼容**：新增一个可选参数 = 新增一个 `WithXXX` 函数，现有调用完全不用改

## 原理拆解

核心就三个东西：

1. **一个 Option 类型**：`type Option func(*Server)` —— 本质是「一个用来修改 Server 的函数」
2. **一堆 WithXXX 函数**：每个返回一个 Option，比如 `WithPort(8080)` 返回「把端口设为 8080 的那个函数」
3. **构造函数遍历执行**：`func NewServer(opts ...Option)` 里先填默认值，再 `for` 循环把每个 option 应用上去

> 这个「把『操作』当成『参数』传」的思想叫**高阶函数**，是 Go 里很常见也很重要的一招。

## 和建造者的区别

- 建造者：`.XXX().XXX().Build()`，链式、有明确的「构建完成」动作
- 函数选项：`NewServer(WithXXX(), WithXXX())`，把选项**塞进构造函数参数**，更简洁

Go 社区里，**函数选项是更被推荐的主流做法**。建造者模式在 Go 里反而不太常见（更多出现在 Java 系）。

## 何时用 / 何时不用

**用**：构造函数有「可选参数」需求，或未来很可能要加可选参数。

**别用**：参数就一两个、未来也不会变，直接普通构造函数即可。

## 一句话总结

> Go 没有默认参数，函数选项模式就是 Go 对「可选参数」的标准答案——学会它，走遍 Go 生态都不怕。
