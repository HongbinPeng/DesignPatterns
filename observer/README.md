# 观察者模式（Observer）

> **一句话**：一个对象（主题）状态变化时，自动通知所有关注它的对象（观察者）。

## 生活中的类比 📱

你关注了一个公众号。公众号（主题）一发新文章，你和其他所有关注者（观察者）都会自动收到推送。

关键点在于：**公众号不需要知道「具体是谁」在关注它**，它只管「有新文章了就群发通知」；而你可以随时关注（订阅）、随时取关（退订），都不影响公众号继续运转。

**观察者模式，就是这种「一对多的订阅-通知」机制。**

## 它解决什么问题？

后端有一个高频场景：**一件事发生，要联动做一堆事，而且这些事还会不断增减。**

比如「用户下单成功」之后，要：
- 发短信通知 ✅
- 发邮件通知 ✅
- 扣减库存 ✅
- 送积分 ✅
- （以后可能还要）推送 App 通知、写审计日志……

如果把这些逻辑**硬编码**在「下单」函数里，每加一种通知，都要改下单函数——很快下单函数就爆炸了，而且各个通知之间、通知和下单之间耦合得死死的。

观察者模式把「下单」变成主题（Subject），把「发短信/发邮件/扣库存」变成一个个观察者（Observer）。主题状态一变（下单成功），就 `Notify` 所有观察者。**加一种通知 = 注册一个新的观察者，主题代码不动。**

## 应用场景（Go 后端）

- **事件通知**：订单/支付成功后，触发短信、邮件、积分、库存等多方联动
- **发布-订阅**：消息总线、事件总线（简化版就是观察者模式）
- **状态监控**：服务健康状态变化时通知告警、日志、面板
- **配置热更新**：配置变了，通知所有用到的模块

## 优势 ✅

1. **解耦**：主题和观察者互相不知道具体细节，只通过接口通信
2. **符合开闭原则**：加观察者 = 注册一个新的，主题不用改
3. **一对多广播**：一个状态变化，自动同步到多方
4. **动态增减**：运行时随时订阅/退订

## Go 里怎么写？

两个接口 + 两个角色：

```go
// 观察者接口：收到通知后做什么
type Observer interface {
    Update(event string)
}

// 主题接口：管理观察者、发通知
type Subject interface {
    Register(o Observer)
    Deregister(o Observer)
    Notify(event string)
}
```

主题内部维护一个观察者切片，`Notify` 时遍历调用每个观察者的 `Update`。

> 补充：Go 里的 `channel` 也天然适合做「通知」——实际项目里，更复杂、跨 goroutine 的发布订阅，往往会用 channel 或现成的消息队列（如 Kafka）来实现。观察者模式是理解这些机制的**思想基础**。

## 何时用 / 何时不用

**用**：一个对象的变化需要联动多个对象，且这些联动对象会频繁增减。

**别用**：联动对象固定且很少变，直接顺序调用就行；也别在观察者数量巨大、通知频繁时忘了考虑性能。

## 一句话总结

> 「一件事发生，通知一群人」→ 主题管注册和群发，观察者各管各的响应。
