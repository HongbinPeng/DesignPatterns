# 模板方法模式（Template Method）

> **一句话**：把流程的**骨架固定**下来，其中某些**步骤留给子类/实现去定制**。

## 生活中的类比 ☕

冲咖啡和泡茶的流程惊人地相似：

1. 烧水
2. 冲泡（咖啡粉 or 茶叶 ← **这步不同**）
3. 倒进杯子
4. 加调料（奶糖 or 柠檬 ← **这步也不同**）

「烧水 → 冲泡 → 倒杯 → 加调料」这个大骨架是固定的，但「冲泡」和「加调料」两个步骤，咖啡和茶各有各的做法。

**模板方法模式，就是把「固定的大流程」写死，把「可变的步骤」留成钩子（hook）让别人填。**

## 它解决什么问题？

后端经常有这种需求：**一类业务的整体流程是固定的，但中间某个环节的实现各不相同。**

比如数据迁移/导入导出，流程永远是：

```
读取数据 → 转换数据 → 写入目标
```

但「读什么、怎么转、写到哪」针对 CSV、JSON、Excel 各不相同。

如果为每种格式各写一套完整流程，那「读取→转换→写入」这个骨架会被复制粘贴 N 份，哪天要统一加个「进度上报」或「错误重试」，就得改 N 个地方。模板方法把**骨架抽出来写一次**，可变步骤交给不同实现。

## 应用场景（Go 后端）

- **数据导入/导出**：读取→转换→写入，格式可替换
- **支付流程**：下单→支付→回调→记账，支付渠道可替换
- **代码生成器、批处理任务**：固定执行框架，业务步骤可插拔
- **测试基类/脚手架**：统一的 setUp / tearDown 骨架

## 优势 ✅

1. **复用骨架**：通用流程只写一次，避免重复
2. **控制流程**：流程的「先做什么、后做什么」由框架牢牢控制，不易出错
3. **易扩展**：新增一种格式/渠道，只需实现可变步骤，骨架不用动
4. **符合开闭原则 + 好莱坞原则**（"别调用我们，我们会调用你"）

## Go 里怎么写？（和 Java 不太一样）

Java 用抽象类 + 继承实现模板方法。Go **没有继承**，通常用**接口 + 函数**来实现，更简洁：

```go
// 1. 定义一个接口，包含所有步骤（可变的部分）
type Processor interface {
    Read() string
    Transform(string) string
    Write(string)
}

// 2. 模板方法 = 一个固定骨架的函数，调用接口的步骤
func RunPipeline(p Processor) {
    data := p.Read()        // 固定顺序
    result := p.Transform(data)
    p.Write(result)
}
```

`RunPipeline` 就是那个「模板方法」——流程顺序写死了，但每一步具体怎么做，由传入的 `Processor` 实现决定。

> 进阶：如果还想在骨架里加「钩子」（比如一个可选的 `ShouldSkip` 判断），Go 里也可以通过接口方法 + 默认实现的方式做到。初学先掌握上面这个最核心的形式即可。

## 何时用 / 何时不用

**用**：多个流程共享同一套固定骨架，只有个别步骤不同。

**别用**：流程本身不稳定、经常要改顺序，那固定骨架反而碍事。

## 一句话总结

> 「大流程固定、小步骤可变」→ 把大流程写成模板，小步骤留成接口。
