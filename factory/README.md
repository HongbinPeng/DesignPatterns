# 工厂模式（Factory）

> **一句话**：把「**创建哪个具体对象**」的决定权，从调用方手里交给一个专门的「工厂」。

## 生活中的类比 🏭

你去麦当劳点餐，不会自己跑到后厨揉面、炸鸡、包汉堡。你只要对着柜台喊一句「来份巨无霸套餐」，后厨（工厂）会根据你的要求，把对应的东西做好递给你。

你不需要知道「巨无霸」具体是怎么做出来的，更不需要关心厨房里有几台炸锅。你要的只是「结果」——一个做好的汉堡。**工厂模式，就是这个「柜台 + 后厨」。**

## 它解决什么问题？

先看一段「没有工厂」的代码，后端里太常见了：

```go
if payType == "alipay" {
    return &Alipay{...}
} else if payType == "wechat" {
    return &WechatPay{...}
} else if payType == "union" {
    return &UnionPay{...}
}
```

问题在哪？——**这段判断逻辑散落在各处**。每加一种新支付方式，所有写这段逻辑的地方都要改。而且调用方被迫要了解「有哪些实现」，和具体类型死死耦合。

工厂模式把「创建对象的逻辑」**收拢到一个地方**（工厂函数），调用方只依赖抽象接口，不再关心具体是谁、怎么做。

## 应用场景（Go 后端）

- 多种**支付方式**（支付宝/微信/银联）
- 多种**消息通知**（短信/邮件/推送/企业微信）
- 多种**存储引擎**（MySQL/PostgreSQL/内存）
- 根据配置/参数，动态创建不同的处理器、解析器

## 优势 ✅

1. **创建逻辑集中**：改一处，全项目生效，不再到处复制粘贴 if/switch
2. **调用方解耦**：调用方只依赖接口 `Payment`，不依赖具体类型，好替换、好测试
3. **扩展方便（开闭原则）**：新增一种支付，只需加一个实现 + 工厂里多一个分支，老代码不用动
4. **命名清晰**：工厂函数名 `NewPayment(payType)` 本身就是一份「使用说明书」

## Go 里怎么写？

Go 没有类，工厂模式通常就是一个**返回接口的构造函数**（工厂函数），这是最地道、最常见的写法：

```go
// 工厂函数：根据类型返回不同的实现（返回的是接口）
func NewPayment(payType string) (Payment, error) {
    switch payType {
    case "alipay":
        return &Alipay{}, nil
    case "wechat":
        return &WechatPay{}, nil
    default:
        return nil, fmt.Errorf("不支持的支付方式：%s", payType)
    }
}
```

> 进阶：`interface{}` 是 Go 里另类的「万能工厂」，但通常不建议，因为丢了类型安全。老老实实返回具体接口更好。

## 和策略模式、建造者的区别（别搞混）

- **工厂**：关心「**创建**哪个对象」
- **策略**：关心「**用**哪种算法」，对象通常已经存在，只是换行为
- **建造者**：关心「怎么**一步步**搭出一个复杂对象」

三者的边界在真实项目里会有点模糊，但抓住「它主要解决创建 / 行为 / 复杂构建」这个主轴就不慌。

## 何时用 / 何时不用

**用**：创建逻辑有分支、会频繁扩展，且希望调用方和具体实现解耦。

**别用**：只有一个实现、未来也不会多，那就直接 `new` 得了，别为抽象而抽象。

## 一句话总结

> 当「new 谁」这件事需要根据条件动态决定、且经常要加新种类时，把决定权交给工厂。
