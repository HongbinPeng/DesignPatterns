# 适配器模式（Adapter）

> **一句话**：把一个「跟你不兼容」的接口，**翻译**成你想要的接口，让本来搭不上的两样东西能配合工作。

## 生活中的类比 🔌

出国旅行，你带了个国标插头的充电器，结果酒店插座是英标的——插不进去。

怎么办？买个**转换插头（适配器）**：一头插进英标插座，另一头接你的国标充电器。两边谁都不用改，加个「翻译」就通了。

**适配器模式，就是软件世界里的「转换插头」。**

## 它解决什么问题？

后端几乎天天碰到这个场景：**接入第三方 SDK，或者更换底层实现，但它们的接口跟你项目里已经定义好的接口对不上。**

比如你的项目统一规定短信都用 `SmsSender` 接口（`Send(phone, content)`）。但现在要接阿里云，阿里云 SDK 提供的是 `SendMessage(mobile, text)`；换腾讯云，它又提供 `PushSms(phoneNumber, body) (bool, error)`。

如果直接把这些五花八门的接口散落进业务代码，一旦换供应商，所有调用处都要改。适配器模式就是：**为每个第三方 SDK 写一个「转换器」，把它们的接口统一适配成你的 `SmsSender` 接口。**

业务代码永远只认 `SmsSender`，换供应商 = 换一个适配器，业务代码零改动。

## 应用场景（Go 后端）

- **对接不同第三方 SDK**：短信、支付、邮件、推送、对象存储（OSS/S3/COS）
- **多数据源统一**：MySQL、PostgreSQL、ES……适配成统一的「仓储」接口
- **新旧系统兼容**：老接口和新接口不一致时，写适配器平滑过渡
- **隔离第三方依赖**：把「不稳定、可能更换」的外部库，隔离在适配器之后

## 优势 ✅

1. **解耦**：业务代码只依赖自己的稳定接口，不依赖第三方 SDK 的具体形态
2. **可替换**：换供应商、换底层实现，只改/换适配器，业务代码不动
3. **隔离风险**：第三方 SDK 的「脏接口」「怪返回值」都被挡在适配器里
4. **方便测试**：测试时可以 mock 掉适配器，不用真的调用第三方

## Go 里怎么写？

Go 里适配器就是「**用一个结构体包住第三方对象，再实现你要的接口**」：

```go
// 你项目里统一的接口
type SmsSender interface {
    Send(phone, content string) error
}

// 第三方 SDK（接口跟你的不一样，且你改不了它）
type AliyunSmsSDK struct{}
func (a *AliyunSmsSDK) SendMessage(mobile, text string) error { ... }

// 适配器：包住 SDK，实现你的接口
type AliyunAdapter struct {
    sdk *AliyunSmsSDK
}

// 关键：把你的接口方法，翻译成 SDK 的方法
func (a *AliyunAdapter) Send(phone, content string) error {
    return a.sdk.SendMessage(phone, content)  // 参数对调、名字转换都在这做
}
```

> 小提示：适配器（翻译接口）和装饰器（包装加功能）长得有点像，都持有另一个对象。区别在于——**适配器是「把不兼容的接口变成兼容」，装饰器是「接口一样，只加功能」**。

## 何时用 / 何时不用

**用**：两个接口不兼容、又都想用；或想隔离可能频繁更换的第三方依赖。

**别用**：接口本来就能直接对上，就别套一层无意义的适配器。

## 一句话总结

> 两边接口对不上、又都不好改？中间加个适配器做「翻译官」。
