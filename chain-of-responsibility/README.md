# 责任链模式（Chain of Responsibility）

> **一句话**：把请求交给一条「链」，链上的每个节点依次处理，能处理就处理，不能处理就传给下一个。

## 生活中的类比 🏢

你请假 3 天，要审批。流程是：**主管 → 经理 → 总监**。

- 主管能批 3 天以内的，你请 3 天，主管直接批了，流程结束 ✅
- 你要是请 10 天，主管没权限，就**把申请往上一级传**，经理也批不了，继续传到总监……

每个审批人只关心两件事：「我能批吗？能就批；不能就传给下一个。」**责任链，就是这条「审批流水线」。**

## 它解决什么问题？

后端有两种非常典型的场景：

**场景一：层层审批/校验**。一个请求进来，要经过权限校验 → 参数校验 → 限流 → 业务处理……每一步都可能「拦住」请求，或把它放行给下一步。

**场景二：HTTP 中间件**。Go 里 `net/http` 的中间件链就是责任链——请求经过日志中间件、鉴权中间件、业务 handler，一层层传递。

如果用一堆嵌套的 if-else 来写，代码会变得又长又僵硬。责任链把「每一步」拆成独立的节点，节点之间只通过「下一个节点」的指针相连，**灵活增删、调整顺序**。

## 应用场景（Go 后端）

- **审批流**：请假、报销、采购的多级审批
- **HTTP / gRPC 中间件**：日志 → 鉴权 → 限流 → 业务
- **请求校验链**：参数校验 → 权限校验 → 风控校验
- **过滤链**：敏感词过滤、日志脱敏

## 优势 ✅

1. **职责单一**：每个节点只处理自己的事，逻辑清晰
2. **灵活可编排**：节点的**顺序、增删**都可以动态调整
3. **解耦发送者和接收者**：请求方不知道具体是谁处理了它
4. **可复用**：单个节点（比如鉴权）可以在不同链里复用

## Go 里怎么写？

核心是一个「处理者」接口 + 一个「下一个节点」的引用：

```go
type Approver interface {
    SetNext(next Approver) Approver
    Handle(req *LeaveRequest)
}
```

每个节点：**能处理就返回，不能处理就调用 `next.Handle(req)`**。

> 常见做法是用一个「基础处理者」结构体，把 `next` 字段和「传下去」的通用逻辑放进去，具体节点只实现自己的判断逻辑（Go 里靠结构体嵌入来复用这部分）。

## 何时用 / 何时不用

**用**：一个请求需要被多个处理器**依次**处理，且处理顺序/组合可能变化。

**别用**：处理步骤固定且不会变，顺序调用即可；也别让链太长（比如上百个节点），否则难调试、性能也受影响。

## 和装饰器模式的区别

它俩都像「层层包裹」，但注意方向不同：

- **装饰器**：强调「**加功能**」，外层装饰器会在调用内层前后做额外的事，请求一般会贯穿整条链
- **责任链**：强调「**找能处理的人**」，某个节点处理完就可以**终止**，不一定走完整条链

## 一句话总结

> 「一件事可能要经过多个环节，能办就办、不能办就往下传」→ 责任链。
