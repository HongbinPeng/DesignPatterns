# 装饰器模式（Decorator）

> **一句话**：**不改动原有代码**，给它「包一层」，动态地添加新功能。

## 生活中的类比 🧅

洋葱，或者更贴切——**快递包装**。

你要寄一个易碎品：先把东西装进盒子（核心功能），然后包一层气泡膜（防震），再套一个纸箱（加固），最后贴上面单（记录信息）。

每一层「包装」都不改变里面东西本身，但叠加起来，就让一个普通的盒子具备了防震、加固、可追踪等能力。而且你可以按需选择包几层、包哪些层。

**装饰器模式，就是给对象一层层「包包装」的能力。**

## 它解决什么问题？

假设你写好了数据读取的核心逻辑，突然老板说：「给所有读取加个日志」「热门数据要加缓存」「再加个限流」。

最笨的办法是**直接改核心代码**，把日志、缓存、限流的逻辑全都塞进原来的函数里。很快，这个函数就变成一坨谁也看不懂、一改就出 bug 的「上帝函数」。

装饰器模式的做法是：**核心代码一行不动**，另外写几个「装饰器」，像包装纸一样把核心对象包起来。每个装饰器只负责一件事（记日志 / 缓存 / 限流），需要哪个功能就包哪一层。

## 应用场景（Go 后端）

- **HTTP 中间件**（最常见！）：给 handler 包上日志、鉴权、限流、CORS……Go 的 `net/http` 中间件本质就是装饰器
- 给数据访问加**缓存层**
- 给函数加**计时、重试、熔断**
- 给输出加**加密、压缩**（一层套一层）

## 优势 ✅

1. **符合开闭原则**：对「扩展」开放（随便加装饰器），对「修改」关闭（核心代码不动）
2. **职责单一**：每个装饰器只管一件事，清晰、易测试、可复用
3. **灵活组合**：功能像积木一样，想加就加、想拆就拆、顺序还能调
4. **比继承更轻**：不用搞复杂的继承树，就是「接口 + 组合」

## Go 里怎么写？

关键在于：**装饰器实现和核心对象同一个接口，并且内部持有（包着）一个同接口的对象**。

```go
type DataSource interface {
    Read(key string) (string, error)
}

// 核心实现
type MemorySource struct{ ... }        // 实现 DataSource

// 日志装饰器：也实现 DataSource，里面「包着」另一个 DataSource
type LoggingSource struct {
    inner DataSource                    // ← 被包装的对象
}

func (l *LoggingSource) Read(key string) (string, error) {
    fmt.Println("读 key:", key)          // 先干自己的活（加日志）
    return l.inner.Read(key)             // 再委托给被包装的对象
}
```

装饰器的套路就一句话：**先做自己的事，再把请求转发给 `inner`**。

## 何时用 / 何时不用

**用**：想给现有对象**在不改代码**的前提下动态加功能，且功能能自由组合。

**别用**：功能加得太多、层次太深时，调用栈会像「俄罗斯套娃」一样难调试，要克制。也别为了「以后可能用」而提前套一堆装饰器。

## 一句话总结

> 想给代码加功能又不想改它？写个实现同一接口的「包装类」，把请求转发给被包装对象即可。
